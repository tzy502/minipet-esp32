## 二、现状盘点（读码结论）

### 2.1 菜单结构现状 ✅
- 已是「主菜单 → 地图 → 地图列表」两级；列表项 = `asset_dl_bgmap_list()` 给的
  `(hash, label, cached)`，**点列表项=立即切图**（`MP_CMD_SET_MAP`），无二级功能菜单。
- 列表有"已缓存优先"重排（`menu_items_cached_first`）；label 显示宽 32 字节（~10 个汉字）。

### 2.2 地图名"数字编号"问题的真相 ✅
manifest 里 BGMAP 的 label 有两种来源：
| 来源 | label 实例 | 相貌 |
|---|---|---|
| Web/常规登记（旧 950KB 包） | `神秘岛：天空之城售票处`、`射手村：射手村` | **本来就是中文** |
| push 端点直推（新 237KB 包，`EnsureMapAsync`） | `map_000010000`、`map_004000030` | 兜底字符串=**"数字编号"的来源** |
- 结论：**中文名的数据源存在**（旧登记走的是带名渠道），新 push 端点没接上这个名字源
  （`AssetExporter` 地图路径没有查 WZ MapName，只有 NPC 路径有 `npcName`）。
- 所以"数字编号转中文"的正确修法是**服务端 push 登记时把 WZ 地图名写进 label**
  （根因层）；设备侧"数字→中文数字"兜底转换是第二层保险。

### 2.3 设备视口/相机现状 ✅
- 每张地图只烘焙了 **240×240（1x）一个相机窗口**（导出相机=地图中心或 clock 锚点，
  `ClampCamera` 夹取后固定），设备拿到的像素只有这一窗。
- 相机位移能力现状：仅 §14.5 的 Y 向 248px 实验（已按板配置化 `ground_cam_shift_px`，
  板A=0）。**没有 X 向、没有用户可调、没有持久化**。
- 条带模型已具备视差要素：wire strip 带 `y / speed_x / rx_parallax`，合成按 y×2 定位、
  按 speed 滚动、按 rx 做 IMU 视差——与桌宠 back 视差模型同构。
- 站位地面线：`kGround000010000[240]` 按当前视口逐列烘焙 + 通用线兜底（屏底-20）；
  相机一动，这张表不跟着动（联动缺口，见 5.4）。

### 2.4 桌宠参考实现（摄像机语义）✅ —— 本需求的"标准答案"
读 `MapViewportWindow.cs`：
- 相机状态 = `(_camX, _camY, _zoom)`，**初始=地图中心、zoom=1**；
- **左键拖拽平移**：`camX -= dx/zoom`（跟手、方向为"抓地图"）；
- **滚轮缩放 0.25~4**，以光标为锚（world = cam + (mouse−screenCenter)/zoom 换算）；
- 每帧 `ClampCamera`（=桌面 `Camera.AdjustToWorldRect`：相机中心夹在
  `[Min+half, Max−half]`，地图小于视口时居中）——**相机永不出地图边界**；
- back 层视差按 camCenter 实时重渲，滚动层按 viewTimeMs 自动播；
- **不跟随宠物**——背景模式相机纯手动。
- 桌面能这么干是因为它每帧从 WZ 图层**按视口现渲**，全图数据常在。

### 2.5 字体现状 ✅
| 资产 | 覆盖 | 用途 | 格式 |
|---|---|---|---|
| `menu_font_cn.c`（flash 烘焙 22px） | **123 字**（源码字符串自动提取）；数字汉字 14 个只含"一" | LVGL 菜单 | LVGL C 数组 |
| TF 上 FONT 3 档（16/24/32px） | 3892 字（常用 CJK 全覆盖） | 合成器气泡/文本 | 自研 mpak（**LVGL 读不了**） |
| LVGL 9.6 `binfont_loader` | — | **组件在库，`lv_binfont_load(path)` 可用**，需配 lv_fs 驱动 | LVGL bin |
| FreeType（managed_components） | — | 在库未用于菜单 | TTF 运行时渲染 |
- "TF 烧字库"**可行性结论：可行**——LVGL 9 binfont + `LV_USE_FS_STDIO`（或自注册
  lv_fs 驱动挂 `/sdcard`）即可让菜单从 TF 加载全量中文字库；22px 常用 3500 字 bin 约
  1MB 上下，TF 容量无压力。生成脚本与 `regen.sh` 同款（`lv_font_conv --format bin`）。
- 烘焙子集（现状机制）永远追不上**服务端动态下发**的地图名——这是上 TF 字库的核心理由。

## 三、变更点 1：地图列表中文化

### 3.1 需求表述
列表里不允许出现 `map_000010000` 这类裸编号；已登记图显示中文名；万一仍是纯数字
（无名图），设备侧以中文数字兜底显示（如 `200000100` → `二〇〇〇〇〇一〇〇`）。

### 3.2 分层修法
| 层 | 改动 | 效果 |
|---|---|---|
| L1 服务端（根因） | `EnsureMapAsync` 登记 BGMAP 时查 WZ MapName 写 label（NPC 路径已有同款先例 `npcName`） | 新登记图直接中文名 |
| L2 设备兜底 ✅已拍板 | 列表渲染时检测 `^map_\d+$` 前缀 → **剥掉前缀直接显示阿拉伯数字原名**（如 `map_000010000` → `000010000`） | 无名图可读、零字库负担 |
| L3 字库 | 见 3.3 | 中文名（动态下发）都显示得出来 |

### 3.3 字库方案对比
| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| F1 扩烘焙子集 | regen.sh 机制自动提取源码用字，把数字汉字/界面新词写进源码即可 | 零新架构，+15 字 ≈ +6KB flash | **覆盖不了服务端动态名** | 必做（兜底） |
| **F2 TF 字库** | `lv_font_conv --format bin` 烘 22px 常用 3500 字 → TF；`lv_binfont_load` + lv_fs stdio 驱动；字体查找链 TF→烘焙子集→Montserrat | 动态中文名全覆盖；"TF 烧字库"正解；服务端后续可经 FONT 通道更新 | 需 lv_fs 驱动接入 + 字体加载失败兜底；首载 ~几十 ms | **推荐（主）** |
| F3 FreeType | 运行时渲 TTF | 任意字号 | 内存/CPU 开销大、卡顿风险 | 不推荐一期 |

🔢 拍板点：F2 的字库 .bin **投放方式**——(a) 调试期 TF 卡手动拷一次；(b) 服务端
FONT 通道扩展下发（mpak 是自研字形格式，装 LVGL bin 需新 kind 或裸文件通道）。
建议先 (a) 跑通，(b) 二期。

### 4.2 ①选择此地图为背景
= 现行为搬进子页（`MP_CMD_SET_MAP`+`asset_dl_touch` LRU）。验收不变：切换成功、
随机表情反馈、断电重启后仍为当前图（现行为）。

### 4.3 ②修改当前地图的摄像头 → 见第五节（重点）

### 4.4 ③删除此地图 ✅ 已拍板（2026-10-01）：本地隐藏标识制
- **语义**：不物理删文件——本地打"用户隐藏"标识：列表不再显示、LRU 照常管空间；
  **服务端再次推送该图时（push 指令到达）自动解除隐藏**、恢复列表并可选用。

- 边界用例：隐藏当前正在渲染的图 → 立即切回默认图 000010000；隐藏全部图 → 同上；
  隐藏标识存 NVS per-map，重启保持。

## 五、重点：摄像机功能

### 5.1 目标语义（对齐桌宠，2.4 节读码结论）
> 相机 = 世界坐标点；初始=地图中心（或该图 clock 锚点）；用户拖拽平移（跟手）；
> 夹取在地图有效范围内永不出界；按 map 持久化，**每次加载该图全局应用**（"全局加载"
> 的落点）；状态断电不丢。一期不做缩放（桌面 0.25~4 缩放列为二期）。

### 5.2 核心矛盾：像素从哪来 ✅ 已拍板（2026-10-01）：**必须全图加载**
- 用户原话：「我需要全屏 整个全部加载 不行的话考虑服务端选择地图在下发；
  **全屏选择是必须满足**，展示的地图没有实际地图的 10%」。
- 实测：当前 240×240 窗口占 000010000 全图（2270×1807）的 **1.4%**——用户不满完全属实。
- 结论：R2（全图 TF 常驻 + 相机任意平移）提为一期硬性需求；1.5×/2× 扩窗方案否决；
  服务端"选区截取下发"降为 Plan-B 备选。

#### R2 可行性数学（已验证）
| 项 | 数值 | 判定 |
|---|---|---|
| 全图体量（000010000 最图） | static 8.2MB + tile 8.2MB + mask 0.5MB ≈ **16.9MB/图** | TF 16GB 无压力（10 图 170MB） |
| PSRAM（8MB） | 全图**不驻留**，分块缓存 ~0.6-0.9MB（如 240×240 设备px 块 ×6 LRU）；峰值 ~3.3-4MB | **反而比 2× 驻留方案省** ✓ |
| 平移带宽 | SDMMC 1-bit 实效 2-4MB/s；整窗换位读 ~700KB ≈ 200-350ms；**边缘增量读**（拖动只读新露出的边条 ~115-230KB）→ 拖动 **8-15fps**，相机静止零 TF 读取、30fps 满帧 | 设置交互可接受（非 30fps 丝滑，明确预期） |
| 随机读 | `mpak_read_at()` 现成（Range 下载/层装载已在用） | 固件零新原语 ✓ |
| 服务端整图渲染 | **现成**：模式1 `RenderMapFull` = RenderViewport(全图尺寸) 快照（桌面 crop/预览共用）；分两趟出 static+tile 与现管线同构 | 导出端改视口参数即可 ✓ |
| BGMAP 头容量 | vw/vh u16（2270×1807 装得下）；mask/偏移字段同构 | 格式不破 ✓ |
| 下载时长 | 17MB 局域网 Range 续传 ≈ 15-60s/图，每图一次性 | 需进度提示（菜单/气泡） |
| u16 溢出保护 | 超大图（>65535px 或 TF 配额）导出端拒绝/裁剪 | 导出端加上限策略 |

#### 导出与合成的两个格式要点
1. **视差层不进整图**：rx=0 且 speed=0 的 back 段可烘进整图 static；**rx≠0/speed≠0
   条带必须保持独立带层**（全图宽×带高，TF 常驻或 PSRAM），设备按相机偏移×视差系数
   叠加——否则视差失效（桌宠的 back 视差是按 camCenter 实时算的，整图烘焙表达不了）。
2. **真 foothold 地面表（顺带收官）**：服务端按 foothold 第 0 层（`GetGroundY` 现成）
   导出**全宽逐列地面 Y 表**（2270 字节/图）随 BGMAP 下发，替换现在 240 列烘焙表——
   宠物站在"真 foothold"上这条悬了很久的需求在全图方案里自然闭环。

#### 零缩放纪律 ✅（2026-10-01 用户要求，硬约束）
- **素材侧**：全图按原生 1x 分辨率导出存储，**禁止任何降采样/缩略**（17MB/图 就是 1x 的代价，接受）。
- **设备侧**：全链路只允许**整倍像素加倍**（1x→2x，每素材像素=屏上 2×2 同色块，与桌宠
  RenderViewport(zoom=2) 同口径）；相机平移整数像素对齐；**任何非整倍插值/重采样一律禁止**
  （板B 360 屏的 1.5x 泛化路径仅限板B，板A 480 不得触发非整倍）。
- 取证基线：字节对拍 static 行首 `bf7f bf7f beff beff` = 源像素成对重复（纯加倍零插值）；
  验收时用同款逐字节比对终验。

#### ⚠️ "全图加载"≠"全图塞进一屏"（2026-10-01 用户报"地图相对人物变小"澄清，硬约束）
- 用户原话：「把缩放给去掉 现在整个地图相对人物来说变小了」。
- 真相：R2 全图方案里**世界比例不变**——地图 1x、人物 1x，屏上同倍显示（与桌宠完全
  一致，取证：人物画布 97x84 世界px → 屏上 194x168，地图纹理同倍率，源像素成对重复
  零插值）。"地图看起来小"的三个视觉来源，全部不是缩放：
  1. **当前帧显示的是别张图**：帧实拍为 200000000 天空塔阁楼（ПЛАТФОРМА 平台牌），
     该图美术元素（大平台牌/宽栏杆）天然比 000010000 的地面尺度大——不同图美术
     尺度本就不同，非管线缩放；
  2. **对比参照是飞行姿态**：之前帧里宠物=fly 画布 368×258 屏px（翅膀特效占大半），
     站立画布仅 194×168——拿带特效的 fly 和地图比，地图显得小；
  3. **相机看到的是全图的一窗**：全图 2270×1807（1x），一窗 240×240——这正是需要
     相机的原因。**绝不为"塞进一屏"缩小地图**，那才是真正的缩放。
- 结论（硬约束）：**世界像素比例恒定**——人物与地图恒为同一 1x 世界系、屏上同倍；
  "看别处"只能靠移动相机，永远不允许靠缩小地图来实现。

#### 宠物锚定语义 ✅ 已拍板（2026-10-01）：屏中回归制
- 用户原话：「当地图调整以后桌宠固定回归到屏幕正中间，同时加上边界保证桌宠不超过
  显示器范围」。
- 语义：**宠物不需要持久世界坐标**。相机调整（调参确认/取消后的重应用）完成时，
  宠物固定回归**屏幕正中间**、脚踩该处地面线（复用现有 `ent_stand_on_ground_locked`
  站位链，x=屏心）；相机偏移只影响背景与视差条带。
- 边界保证（两层，均已存在，验收项）：
  1. 拖拽全程 `drag_clamp`——显示矩形恒夹在屏内；
  2. 动作切换/画布重展导致出屏 >50% → `ent_bounce_if_offscreen` 弹回贴边。
- 实现含义：调参模式里宠物可隐藏或冻结（防拖拽歧义），确认/取消收尾时执行一次
  "回屏中+站位"；无需引入世界坐标持久化，实现量显著下降。

### 5.3 相机状态与持久化
- 一期：**NVS per-map**（`calib` 或新 namespace：`cam/<mapId>` = (dx,dy) 世界 1x 偏移），
  `render_set_map` 装载时读入应用=「全局加载」；出厂/删除地图时清除。
- 二期（可选）：服务端 manifest `camera_table`（同 clock_table 先例），Web 可改、
  多设备同步；设备本地值作覆盖。

### 5.4 交互与联动（易漏点清单）
1. **模式互斥**：调参态下拖动=平移相机，常态拖动=拖宠物——需要显式"调参模式"
   （进：子页②；出：确认/取消）。调参态建议宠物隐藏或钉在锚点，避免拖拽歧义。
2. **站位联动**：相机 Y 平移后地面线必须跟随——kGround 表按相机偏移做索引平移，
   越界回落"屏底-20"通用线；宠物站位重算（现有 `ent_stand_on_ground_locked` 复用）。
3. **条带联动**：分段条带（speed=0 全视口层）与 static/tile 同一烘焙相机 → 相机平移
   时整体同移；滚动条带（speed_x≠0）继续自走时间轴；rx 视差在平移基础上叠加。
4. **越界夹取**：与桌宠同口径 `ClampCamera`（相机中心 ∈ [Min+half, Max−half]），
   设备侧以"导出窗的世界范围"为边界（R1=窗边界，R2=真地图 bbox）。
5. **确认/取消**：确认→NVS 写入+重合成；取消→恢复进入前状态。建议中键确认/长按取消
   （与现菜单键位同构）。
6. **脏区**：平移=全屏变，走整屏重合成路径（现 `full_recompose`）；拖拽帧率预算
   见 R2 行（R1 驻留模式下 PSRAM 直读，拖拽可满 30fps）。

### 5.5 推荐路线（按拍板更新）
- **一期 = R2 全图方案**（用户硬性要求）：服务端整图导出（static+tile+全宽地面表，
  视差条带保持独立带层）→ TF 常驻 → 设备分块缓存流式合成 + 相机状态机（夹取/NVS
  持久化/调参模式）+ 菜单三功能 + 中文化三层。
- **Plan-B（仅当 R2 联调卡死才启用）**：服务端"选区截取下发"（用户在 Web 上框选
  相机区域 → 服务端裁该区域包 → 推送）——保底可看，但失去设备端自由平移。
- **二期**：服务端 camera_table（Web 可改相机，同 clock_table 先例）、字库服务端
  下发通道、下载进度 UI 优化。缩放已砍，不排期。
- **依赖**：NAS 服务端重部署（链路有先例）+ 存量图全量重导重推（17MB/图 ×N）。

## 六、验收标准（可测）
1. 列表无裸 `map_\d+`；已登记图全中文名；动态中文名缺字率=0（TF 字库覆盖常用 3500 字）。
2. 三功能子页可达可返回；①切图成功且重启保持；③隐藏后列表消失、当前图被隐藏自动回
   默认图、服务端重推同一张图时自动恢复显示。
3. ②调参态：**相机可平移覆盖整张地图**（非一窗），拖动跟手（边缘增量读 8-15fps 级）、
   四向到边有夹取（永不出图边界）、确认后重启应用同偏移、取消不留痕；
   **调参收尾后宠物固定回归屏幕正中间（脚踩地面线）**。
4. 相机移动后宠物站位地面线逐列正确（真 foothold 全宽表，越界回落通用线）；
   **任何时刻宠物不越出屏幕**（拖拽夹取 + 越屏>50% 弹回双保险）。
5. 平移时条带不撕裂不残留（残留自检零告警）；视差条带随相机偏移按系数移动；
   PSRAM 峰值 ≤4.5MB（分块缓存方案）；相机静止时零 TF 读取、渲染 30fps 满帧。
6. 首次下载 17MB 级全图包：Range 断点续传可用、有进度提示、中断后重试能续。
7. **零缩放终验**：全图导出字节与 WZ 原生 1x 渲染逐字节一致（无降采样）；帧缓冲对
   源包做同款字节对拍（成对重复=整倍加倍，无插值）。

### 补充说明 A：窗口尺寸 1.5× vs 2× 到底在选什么
现状：服务端给每张地图"拍的照片"只有**正好一屏大**（240×240 原始像素，屏上 2 倍
铺满 480×480）。想让用户"拖动相机看别处"，照片必须**比屏幕大**——多出来的部分就
是可拖动的余量：
| 档位 | 照片大小 | 上下左右可拖动余量 | 内存代价 | 风险 |
|---|---|---|---|---|
| 1.5× | 360×360（原像素） | 各 **±60** 原始像素（屏上 ±120px ≈ 1/4 屏） | PSRAM 净增 ~+1.2MB → 峰值 ~6.6MB（8MB 内宽裕） | 稳，无需额外动作 |
| 2× | 480×480（原像素） | 各 **±120** 原始像素（屏上 ±240px ≈ 半屏） | PSRAM 净增 ~+2.9MB → 峰值 ~8.3MB（**超 8MB**） | 必须同时做内存纪律：部件缓存上限 2M→1M、LVGL 菜单缓冲改"进菜单才分配"，做完回落 ~6.8MB |
- 拖动余量的体感：1.5× = 能把画面挪到看到旁边"多出 1/4 屏"的内容；2× = 半屏，
  拖起来明显更有"相机在动"的感觉。
- TF/下载代价两档都可忽略（1.5× ≈ 560KB/图、2× ≈ 950KB/图，与旧 950KB 包相当）。
- 服务端导出工作量两档相同（同一个视口参数填不同值）。

### 补充说明 B：字库投放方式（原问题 3 的白话版）
全量中文字库是一个 ~1MB 的文件，要放到板子的 TF 卡上才能被菜单加载。问题是它
**怎么进 TF**：
- (a) **手动拷**（建议先行）：电脑上生成好 → TF 卡用读卡器插电脑拷一次 → 完事。
  字库内容基本不变，一次拷完长期用。调试期这样最快，不依赖任何服务端改造。
- (b) **服务端下发**（二期可选）：把字库当素材走推送通道，板子自动下载进 TF，
  以后换字库不用拔卡。需要服务端加一种"裸文件"素材类型，有改造量。
两步不冲突：先 (a) 把功能跑通，(b) 什么时候要做都行。
